# Dossier de réalisation professionnelle - E6

## 1. Identification

| Élément | Description |
| --- | --- |
| Projet | Application de gestion d'établissement scolaire |
| Formation | BTS Services Informatiques aux Organisations |
| Option | SLAM |
| Type de réalisation | Conception et développement d'une application métier |
| État | Cadrage fonctionnel |

Les informations personnelles du candidat, de l'établissement de formation et de la session seront ajoutées dans les documents officiels fournis par le centre d'examen.

## 2. Contexte et besoin

Un établissement scolaire doit centraliser les informations utiles à la scolarité : élèves, professeurs, classes, matières, notes, absences, documents et emplois du temps.

Le besoin est de proposer un outil unique, accessible selon le rôle de chaque utilisateur, afin de réduire la dispersion des informations et de sécuriser leur consultation ou leur modification.

## 3. Solution retenue

La solution comprend deux interfaces complémentaires alimentées par une API et une base de données communes :

| Application | Public principal | Finalité |
| --- | --- | --- |
| Application légère | Élèves et professeurs | Consulter et gérer les informations de scolarité autorisées |
| Application lourde | Personnel administratif et administrateurs | Administrer les données de l'établissement et superviser l'application |

Le détail des fonctions est disponible dans [Fonctionnalitée.md](Fonctionnalitée.md). Le partage des responsabilités entre les deux applications est défini dans [Separation.md](Separation.md). Les données métier et leurs relations sont décrites dans [MCD.md](MCD.md).

## 4. Utilisateurs et droits

| Rôle | Responsabilités principales |
| --- | --- |
| Élève | Consulter ses informations scolaires et utiliser la messagerie |
| Professeur | Gérer les notes, absences et documents de ses classes |
| Administration | Gérer les élèves, professeurs, classes, matières et documents |
| Administrateur | Gérer les comptes, rôles, paramètres et journal des actions |

Le principe appliqué est celui du moindre privilège : chaque compte ne peut accéder qu'aux données nécessaires à son rôle.

## 5. Exigences de qualité

- Authentification obligatoire et contrôle des autorisations côté serveur.
- Protection des données personnelles et traçabilité des actions d'administration.
- Validation des données saisies.
- Interface lisible et utilisable sur les appareils prévus.
- Documentation du déploiement, des choix techniques, du schéma de données et des tests.
- Versionnement du code et de la documentation dans ce dépôt.

## 6. Éléments à produire pendant le développement

Pour rendre la réalisation démontrable et réutilisable, le dépôt devra progressivement contenir :

1. le code source des deux interfaces et de l'API ;
2. le schéma de la base de données et ses migrations ;
3. la procédure d'installation et de déploiement ;
4. les jeux de données de démonstration ne contenant aucune donnée réelle ;
5. les tests et leur résultat ;
6. les captures ou scénarios de démonstration ;
7. la fiche de présentation de la réalisation professionnelle au format officiel E6.

## 7. Décisions à prendre

Les décisions suivantes restent ouvertes et devront être justifiées dans la documentation technique :

- technologies du front-end, de l'API et de la base de données ;
- hébergement et gestion des fichiers déposés ;
- mode de notification et périmètre de la messagerie temps réel ;
- périmètre de la première version livrable ;
- modèle précis des permissions et des données scolaires.

## 8. Périmètre de la première version

La première version doit prioriser l'authentification, les rôles, la gestion des élèves, professeurs, classes et matières, puis les fonctions de consultation et de saisie des notes et absences. Les fonctions plus complexes, notamment les notifications temps réel et les statistiques avancées, seront intégrées après validation du socle.
